# Todo App

REST API для списков дел на Go с PostgreSQL. Пользователи регистрируются, входят по паролю, создают списки и задачи, редактируют их и отмечают выполнение. Доступ к данным ограничен владельцем.

## Возможности

- Регистрация и вход, JWT с ограниченным сроком действия.
- Хранение новых паролей с bcrypt и автоматическое обновление старых хешей после успешного входа.
- CRUD списков и задач, поле `done` для статуса выполнения.
- Проверка прав пользователя при чтении и изменении данных.
- Транзакции для создания объектов и удаления списка вместе с его задачами.
- Валидация входных данных и единые JSON-ошибки без внутренних подробностей БД.
- Конфигурация через окружение, необязательный `.env`, таймауты и корректное завершение сервера.
- Модульные тесты, проверки SQL-запросов и интеграционный тест API с PostgreSQL.

## Стек

Go 1.24.2+, Gin, sqlx, PostgreSQL, golang-jwt/jwt/v5, bcrypt, Viper, Logrus. Docker Compose используется для локальной базы данных. Приложение запускается на хосте.

## Запуск

### 1. Подготовьте конфигурацию

```sh
git clone https://github.com/bikojii/todo-app.git
cd todo-app
go mod download
```

Скопируйте `.env.example` в `.env` и заполните `DB_PASSWORD` и `JWT_SECRET`. Файл `.env` не должен попадать в Git. JWT-секрет должен содержать не менее 32 байт; используйте случайное значение.

Копирование в Linux/macOS:

```sh
cp .env.example .env
openssl rand -hex 32
```

Копирование и генерация секрета в Windows PowerShell:

```powershell
Copy-Item .env.example .env
$bytes = New-Object byte[] 32
$rng = [System.Security.Cryptography.RandomNumberGenerator]::Create()
$rng.GetBytes($bytes)
$rng.Dispose()
[BitConverter]::ToString($bytes).Replace('-', '').ToLowerInvariant()
```

Запишите сгенерированное значение в `JWT_SECRET` в `.env`. Для пароля БД используйте отдельное значение.

### 2. Запустите PostgreSQL

```sh
docker compose up -d --wait db
```

Compose публикует порт базы только на `127.0.0.1`. Данные сохраняются в Docker volume. По умолчанию используются пользователь `postgres`, база `todo` и порт `5432`.

### 3. Примените миграции

На новой базе выполните обе миграции по порядку. Если `DB_USER` и `DB_NAME` изменены, замените соответствующие аргументы команд.

Linux/macOS:

```sh
cat schema/000001_init.up.sql | docker compose exec -T db psql -v ON_ERROR_STOP=1 -U postgres -d todo
cat schema/000002_indexes.up.sql | docker compose exec -T db psql -v ON_ERROR_STOP=1 -U postgres -d todo
```

Windows PowerShell:

```powershell
Get-Content schema/000001_init.up.sql | docker compose exec -T db psql -v ON_ERROR_STOP=1 -U postgres -d todo
Get-Content schema/000002_indexes.up.sql | docker compose exec -T db psql -v ON_ERROR_STOP=1 -U postgres -d todo
```

На существующей базе со схемой первой версии примените только `000002_indexes.up.sql`. Приложение не применяет миграции автоматически. Файлы `*.down.sql` предназначены для отката; откат первой миграции удаляет таблицы и данные.

### 4. Запустите приложение

```sh
go run ./cmd
```

Сервер доступен по адресу `http://localhost:8000`. Для остановки используйте `Ctrl+C`. Для остановки базы без удаления данных:

```sh
docker compose stop db
```

## Конфигурация

Приоритет: переменные окружения → значения из `.env`, если переменная ещё не задана → `configs/config.yml` → значения по умолчанию. Файлы `.env` и `config.yml` необязательны, если необходимые параметры заданы окружением.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `PORT` | `8000` | Порт HTTP-сервера |
| `DB_HOST` | `localhost` | Хост PostgreSQL |
| `DB_PORT` | `5432` | Порт PostgreSQL |
| `DB_USER` | `postgres` | Пользователь БД |
| `DB_NAME` | `todo` | Имя базы |
| `DB_PASSWORD` | — | Обязательный пароль БД |
| `DB_SSLMODE` | `disable` | Режим TLS-соединения с БД |
| `JWT_SECRET` | — | Обязательный секрет подписи JWT, минимум 32 байта |

JWT действует 12 часов. Поддерживается только HS256. Замена секрета делает ранее выданные токены недействительными. Для удалённой БД настройте подходящий режим TLS; `disable` предназначен для локального запуска.

## API

Все тела запросов — JSON. Для защищённых маршрутов передавайте заголовок `Authorization: Bearer <token>`. Используйте завершающий `/` в маршрутах коллекций, как в таблице.

| Метод | Маршрут | Действие |
| --- | --- | --- |
| POST | `/auth/sign-up` | Регистрация |
| POST | `/auth/sign-in` | Вход |
| POST | `/api/lists/` | Создание списка |
| GET | `/api/lists/` | Списки текущего пользователя |
| GET | `/api/lists/:id` | Получение списка |
| PUT | `/api/lists/:id` | Частичное обновление списка |
| DELETE | `/api/lists/:id` | Удаление списка и его задач |
| POST | `/api/lists/:id/items/` | Создание задачи в списке |
| GET | `/api/lists/:id/items/` | Задачи списка |
| GET | `/api/items/:id` | Получение задачи |
| PUT | `/api/items/:id` | Частичное обновление задачи |
| DELETE | `/api/items/:id` | Удаление задачи |

### Пример последовательности запросов

Регистрация:

```sh
curl -X POST http://localhost:8000/auth/sign-up -H 'Content-Type: application/json' -d '{"name":"Alice","username":"alice","password":"my-password-123"}'
```

Вход:

```sh
curl -X POST http://localhost:8000/auth/sign-in -H 'Content-Type: application/json' -d '{"username":"alice","password":"my-password-123"}'
```

Ответ содержит `{"token":"..."}`. Подставьте токен вместо `TOKEN`:

```sh
curl -X POST http://localhost:8000/api/lists/ -H 'Content-Type: application/json' -H 'Authorization: Bearer TOKEN' -d '{"title":"Работа","description":"Задачи на неделю"}'
curl -X POST http://localhost:8000/api/lists/1/items/ -H 'Content-Type: application/json' -H 'Authorization: Bearer TOKEN' -d '{"title":"Подготовить резюме","done":false}'
curl -X PUT http://localhost:8000/api/items/1 -H 'Content-Type: application/json' -H 'Authorization: Bearer TOKEN' -d '{"done":true}'
curl http://localhost:8000/api/lists/1/items/ -H 'Authorization: Bearer TOKEN'
```

Вместо `1` используйте идентификаторы из ответов создания. Команды выше записаны для POSIX-оболочки; в Windows можно отправлять те же запросы через Postman или `Invoke-RestMethod`.

### Форматы и ограничения

- Регистрация: `name`, `username`, `password`. Пароль — 8–72 байта. Старые учётные записи с более короткими паролями сохраняют возможность входа.
- Список: `title`, `description`.
- Задача: `title`, `description`, `done`.
- Обязательные строки не могут состоять только из пробелов. Текстовые поля ограничены 255 символами.
- В обновлении нужно передать хотя бы одно изменяемое поле. `{"done":false}` и `{"description":""}` допустимы; пустой объект — нет.
- Размер тела запроса ограничен 1 МиБ.
- Неизвестные поля и несколько JSON-объектов в одном запросе отклоняются.
- Пустые коллекции возвращаются как `[]`; список списков имеет форму `{"data":[]}`.

Создание пользователя, списка или задачи возвращает `201` и `{"id":1}`. Чтение и обновление — `200`. Удаление — `200` и `{"status":"ok"}`.

### Ошибки

Формат: `{"message":"..."}`.

| Статус | Значение |
| --- | --- |
| `400` | Некорректный JSON, идентификатор или содержимое запроса |
| `401` | Неверные данные входа, отсутствующий или недействительный токен |
| `404` | Ресурс отсутствует или принадлежит другому пользователю |
| `409` | Имя пользователя уже занято |
| `500` | Внутренняя ошибка; подробности записываются только в журнал |

## Архитектура

```text
HTTP → handler → service → repository → PostgreSQL
```

| Путь | Ответственность |
| --- | --- |
| `cmd/` | Конфигурация, сборка зависимостей и жизненный цикл сервера |
| `pkg/handler/` | Маршруты, JWT middleware, JSON и HTTP-статусы |
| `pkg/service/` | Авторизация, проверка входных данных и бизнес-операции |
| `pkg/repository/` | SQL, транзакции и проверки принадлежности данных |
| `schema/` | Миграции PostgreSQL |
| `configs/` | Несекретные настройки по умолчанию |
| `todo.go`, `user.go` | Модели и входные DTO |
| `errors.go`, `validation.go` | Типовые ошибки и валидация |
| `server.go` | HTTP-сервер, таймауты и завершение |

## Тесты

```sh
go build ./...
go vet ./...
go test ./...
go test -race ./...
```

Проверка `-race` требует C-компилятора и поддерживаемой платформы. Модульные тесты не требуют работающей БД. Они проверяют пароли и JWT, обновление старых хешей, валидацию, SQL-аргументы, откат транзакций, HTTP-статусы и отсутствие утечек ошибок БД.

Для интеграционного теста задайте `TEST_DATABASE_URL`, например для отдельной локальной тестовой базы:

```sh
TEST_DATABASE_URL='postgres://postgres:YOUR_TEST_PASSWORD@localhost:5432/todo_test?sslmode=disable' go test -count=1 ./...
```

В PowerShell сначала задайте `$env:TEST_DATABASE_URL`, затем выполните `go test -count=1 ./...`. Пользователь БД должен иметь право создавать схемы. Тест создаёт уникальную временную схему, применяет миграции, проверяет API двух пользователей и удаляет только собственную схему. Без переменной интеграционный тест пропускается.

GitHub Actions запускает сборку, `go vet`, тесты и детектор гонок с PostgreSQL 16, включая интеграционный сценарий.

## Обновление существующей установки

Задайте новый случайный `JWT_SECRET` и примените вторую миграцию. Старые JWT не поддерживаются. При успешном входе старый формат пароля автоматически заменяется на bcrypt; новые регистрации используют только bcrypt. Изменение пароля или сброс пароля пока не реализованы.

Удаление списков больше не создаёт задачи без списка. Уже существовавшие записи без связей автоматически не удаляются, чтобы обновление не уничтожало старые данные.

## Границы проекта

Это backend без пользовательского интерфейса. Пагинация, refresh-токены, отзыв отдельных JWT, сброс пароля и ограничение частоты запросов пока не реализованы. Для внешнего размещения нужны HTTPS и настройка инфраструктуры.
